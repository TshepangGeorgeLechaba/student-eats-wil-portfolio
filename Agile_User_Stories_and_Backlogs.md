# Student Eats — Agile User Stories and Backlogs

**Module:** PRP37XS — Project Presentation III  
**Project:** Student Eats  
**Agile approach:** Kanban, as documented in the Agile Team Charter

## 1. Purpose

This document records the user stories, product backlog and sprint-planning evidence for Student Eats. It is based on the team's Trello export and Agile Team Charter.

The project aims to connect student food vendors with student customers through a digital marketplace for discovering meals and arranging orders.

## 3. User Stories

User stories describe features from the perspective of the people who will use the platform.

### 3.1 Student registration

**User story:** As a new student, I want to register using my personal details so that I can access Student Eats and begin ordering meals.

**Proposed acceptance criteria:**
- The registration form requests the required details.
- Required fields are validated.
- The user receives clear feedback if the submitted information is invalid.
- Successful registration provides clear confirmation.
- The handling and storage of registration details are verified against the actual implementation.

### 3.2 Login and authentication

**User story:** As a registered student, I want to log in so that I can access the platform.

**Proposed acceptance criteria:**
- The login form accepts the required credentials.
- Invalid credentials produce understandable feedback.
- Successful login leads to the appropriate platform area.
- Authentication behaviour is tested and documented.

### 3.3 Discover meals

**User story:** As a student looking for food, I want to browse and filter meal listings so that I can find options that suit my needs.

**Proposed acceptance criteria:**
- Meal listings display relevant information.
- Available search and filtering options behave as expected.
- Students can open a listing to view its details.
- Results are checked for usability and accuracy.

### 3.4 List meals

**User story:** As a student food vendor, I want to list meals with photographs and relevant details so that other students can discover what I offer.

**Proposed acceptance criteria:**
- The meal form collects the required listing details.
- Required fields are validated.
- The listing displays the supplied information correctly.
- Saving and persistence are verified against the actual implementation.

### 3.5 Cart and order placement

**User story:** As a student customer, I want to add meals to a cart and review my selection so that I can prepare an order.

**Proposed acceptance criteria:**
- A customer can add a meal to the cart.
- Quantities and totals update correctly.
- A customer can remove items or change quantities where supported.
- The checkout flow provides clear order information.
- Order submission and confirmation are tested without claiming a simulated transaction is a live order.

### 3.6 Order tracking

**User story:** As a student customer, I want to view my order status so that I know what is happening with my order.

**Proposed acceptance criteria:**
- The platform displays the available order information.
- Status changes are shown accurately where implemented.
- Missing or unavailable order information is communicated clearly.
- Order persistence and status updates are verified.

## 6. Sprint Planning and Review

The Agile Team Charter identifies weekly planning, daily stand-ups, reviews or demonstrations, and retrospectives as team practices.

During planning, the team should review the product backlog, select work for the next sprint or work period, assign responsibilities, and agree on realistic tasks. During stand-ups, members should communicate completed work, planned work and any impediments. Reviews and retrospectives should help the team evaluate outcomes and identify improvements.

The team's Definition of Done states that a feature should be finished, its design accepted, testing completed successfully, documentation updated, and the feature prepared for use following Product Owner approval.
